# ULTRA v3.2.0 (2026-11-25): v3.1.0's model with an opt-in level-normalised final pass

**Status: signed and published 2026-11-25T15:25:10Z.**

**What it is:**
- A **runtime-only** release. The weights are the v3.1.0 RC2 INT8 bundle, byte for byte (the tar is the v3.1.0 tar under a new name, same sha256). Both LMs (`M5.ulm`, `c4_p0_0_10_40.v2.ulm`) and the scorer `ultra-score` are the v3.1.0 files.
- It adds **Z1**, an opt-in whole-segment RMS gain in the final commit pass:
  - `ultra-engine-commit --rms-norm`;
  - `ultra stream --commit-pass --commit-rms-norm` (the `ultra` binary is not a release asset, as in v3.1.0);
  - **default off**: with the flag off, the output is byte-identical to v3.1.0's.
- It adds the fail-closed side-feature export guard (training-side Python; no release file changes with it).
- The qualification of the model, every headline number and the limits are in the [v3.1.0 record](v3.1.0.md) and the [RC2 record](v3.1.0-rc2.md).

**Gate status, stated plainly:**
- **The headline WER, speed and energy are unchanged from v3.1.0**: same weights, same LMs, same default decoder behaviour. Nothing here improves them.
- **v3.1.0's registered gate misses still apply** (5,540 against 5,489 full-DEV final edits; 800 against 722 live-with-LM panel edits; 722 against 650 final panel edits). v3.2.0 does not close any of them.
- Z1 is opt-in and its evidence is the guard and confirmation below, not a new headline.

**Release:** <https://github.com/neverhuman/jsr/releases/tag/v3.2.0>, published 2026-11-25T15:25:10Z. Tag `v3.2.0`, tag object `e6239becafa6f96872937a23d45c5c76ef1e50f5`, tag commit `6d95f37d320085aa27806e0e83b1538db02a5684` (the build commit, as for v3.1.0).

**Read these carefully:**
- The -20 dB and -30 dB rows are **synthetic attenuation** of the confirmation half; they show that Z1 recovers quiet input, not that real recordings gain that much. At native level the gain is within noise (-0.02 pp, interval [-0.07, +0.03]).
- The S-half guard was first described in a PR text as "clean c4"; the receipt is the final commit pass, as in the table.
- The cross-ISA witness ran on builds of `f04027c` (the #152 head), and the independent x86 oracle ran at `de0443a`. The Python-oracle review is reported to the lead without a build commit, so it is not counted as evidence on the shipped bytes. None of these is recorded as run on the `6d95f37d` release binaries. The evidence for those binaries is the 50-clip x86 preflight, the relative-CPU run, the automatic endpoint gate for the stream CLI and the 8-utterance spot check below.
- **Z1 relative CPU was measured on H0; energy was not re-measured; v3.1.0's x0 energy rows are unchanged.**
- No new full-DEV or speed receipt exists for the default path, because the default path is byte-identical to v3.1.0's on the checks above.

### Automatic endpoint gate

The DEV selection-half evaluation passed all four trigger checks (hangover, EOF, deadline fallback and PCM-cap fallback) and all six accuracy gates. It used `ultra stream --commit-pass` from build `6d95f37d` with signed RC2 INT8 and M5. The paired arms used a 300 ms hangover and an 800 ms deadline for the WER runs. The trigger checks used forced deadline and PCM-cap cases.
